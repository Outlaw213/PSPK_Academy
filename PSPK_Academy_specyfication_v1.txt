# PSPK AKADEMIA — PROMPT IMPLEMENTACYJNY

## ROLA

Jesteś głównym developerem projektu **PSPK Akademia**.

Masz zaprojektować i zaimplementować aplikację zgodnie z poniższą specyfikacją.

Nie upraszczaj wymagań biznesowych bez uzgodnienia. Nie zmieniaj kluczowych reguł procesu. Jeżeli podczas implementacji znajdziesz sprzeczność lub brak techniczny, zatrzymaj się, wskaż problem i zaproponuj rozwiązanie zamiast samodzielnie zmieniać wymaganie.

Projekt ma być przygotowany jako rzeczywista aplikacja produkcyjna, ale rozwijana etapami.

## NAJWAŻNIEJSZA ZASADA

Nie próbuj implementować całego systemu w jednym kroku.

Pracuj iteracyjnie:

1. przygotuj strukturę projektu,
2. backend,
3. bazę danych,
4. modele,
5. migracje,
6. authentication,
7. API,
8. testy,
9. dopiero później frontend WWW i Android.

Po każdym większym etapie uruchom testy i sprawdź, czy poprzednia funkcjonalność nadal działa.

# 1. CEL SYSTEMU

PSPK Akademia jest systemem edukacyjnym Polskiego Stowarzyszenia Pasjonatów Kowalstwa.

System ma umożliwiać prowadzenie uporządkowanych ścieżek edukacyjnych związanych z kowalstwem.

Podstawowy proces:

UCZESTNIK
→ otrzymuje ścieżkę
→ widzi całą ścieżkę
→ wykonuje dostępne zadanie
→ przesyła zgłoszenie
→ instruktor ocenia
→ zadanie zostaje zaliczone albo skierowane do poprawy
→ uczestnik może wykonać kolejną próbę
→ po zaliczeniu zadania odblokowuje się następne zadanie.

Kluczowe jest rozdzielenie:

* zadania,
* prób wykonania zadania,
* zgłoszenia,
* oceny,
* historii.

# 2. KLUCZOWE REGUŁY BIZNESOWE

Te reguły są nadrzędne.

## R1 — cała ścieżka jest widoczna

Uczestnik widzi wszystkie etapy i zadania przypisanej mu ścieżki.

Niektóre zadania mogą mieć status:

* COMPLETED
* AVAILABLE
* IN_PROGRESS
* SUBMITTED
* UNDER_REVIEW
* NEEDS_IMPROVEMENT
* LOCKED

Zadanie LOCKED jest widoczne, ale nie może zostać rozpoczęte.

---

## R2 — kolejność zadań

Uczestnik nie może wykonać kolejnego zadania, dopóki poprzednie zadanie nie zostało zaliczone.

Przykład:

Task 1 = PASSED
Task 2 = AVAILABLE
Task 3 = LOCKED

Po zaliczeniu Task 2:

Task 3 = AVAILABLE

Źródłem prawdy jest backend.

Frontend nie może samodzielnie decydować o odblokowaniu zadania.

---

## R3 — brak limitu prób

Uczestnik ma nieograniczoną liczbę prób.

Nie implementuj:

MAX_ATTEMPTS.

Przykład:

Attempt 1 → NEEDS_IMPROVEMENT
Attempt 2 → NEEDS_IMPROVEMENT
Attempt 3 → NEEDS_IMPROVEMENT
...
Attempt 100 → NEEDS_IMPROVEMENT
Attempt 101 → może zostać utworzona.

---

## R4 — każda próba jest zachowywana

Nigdy nie nadpisuj poprzedniej próby.

Każde zgłoszenie musi mieć:

* własne ID,
* numer próby,
* datę utworzenia,
* autora,
* zdjęcia,
* komentarz,
* status,
* instruktora,
* ocenę.

Historia musi pozostać dostępna.

---

## R5 — zaliczenie jest ostateczne

Jeżeli instruktor zaliczy zadanie:

Task = PASSED

jest to ostateczne zaliczenie tego zadania.

Nie można tworzyć kolejnej próby tego samego zadania po jego zaliczeniu.

---

## R6 — instruktor

Zgłoszenie trafia do grupy instruktorów posiadających uprawnienia do odpowiedniej ścieżki/etapu.

Pierwszy instruktor, który podejmie zgłoszenie, zostaje jego oceniającym.

Po przejęciu zgłoszenia inni instruktorzy nie mogą równolegle oceniać tego samego zgłoszenia.

Operacja claim musi być atomowa i zabezpieczona przed race condition.

---

## R7 — ocena

Instruktor może:

* zaliczyć,
* skierować do poprawy.

Jeżeli wybiera NEEDS_IMPROVEMENT, komentarz jest wymagany.

Jeżeli wybiera PASSED, zaliczenie jest ostateczne.

---

## R8 — maksymalnie 10 zdjęć

Jedno zgłoszenie może zawierać maksymalnie 10 zdjęć.

Próba wysłania 11 lub większej liczby zdjęć musi zostać odrzucona przez backend.

---

## R9 — kompresja zdjęć

Zdjęcia powinny być kompresowane przed wysłaniem.

W Androidzie kompresja powinna odbywać się przede wszystkim po stronie urządzenia.

Backend również musi walidować:

* MIME type,
* rozmiar,
* liczbę plików.

---

## R10 — AI nie zalicza zadania

AI może pomagać w tworzeniu opisu lub analizie materiału, ale nie może samodzielnie podjąć decyzji o zaliczeniu zadania.

Decyzję o zaliczeniu podejmuje instruktor.

---

## R11 — backend jest źródłem prawdy

Backend kontroluje:

* role,
* dostęp,
* przypisanie do ścieżki,
* dostępność zadania,
* możliwość utworzenia próby,
* możliwość oceny,
* możliwość przejęcia zgłoszenia.

Nigdy nie ufaj frontendowi.

# 8. LOGIKA DOSTĘPNOŚCI ZADANIA

Utwórz jedną centralną funkcję serwisową:

is_task_available(
user_id,
task_id
)

Logika:

1. Użytkownik musi posiadać aktywne Enrollment.
2. Task musi należeć do tej ścieżki.
3. Jeżeli jest pierwszym zadaniem ścieżki → AVAILABLE.
4. Jeżeli nie jest pierwszym:

   * znajdź poprzednie zadanie,
   * znajdź ostatni stan jego realizacji,
   * jeżeli poprzednie zadanie = PASSED → AVAILABLE,
   * w przeciwnym przypadku → LOCKED.

Jeżeli aktualne zadanie ma aktywną próbę:

* SUBMITTED → SUBMITTED
* UNDER_REVIEW → UNDER_REVIEW
* NEEDS_IMPROVEMENT → użytkownik może utworzyć nową próbę
* PASSED → PASSED

Po PASSED:

create submission musi zwrócić błąd.

# 10. TWORZENIE SUBMISSION

Endpoint:

POST /api/v1/tasks/{task_id}/submissions

Backend:

1. sprawdza użytkownika,
2. sprawdza Enrollment,
3. sprawdza dostępność Task,
4. sprawdza czy Task nie jest PASSED,
5. wylicza kolejny attempt_number,
6. tworzy Submission,
7. zapisuje zdjęcia,
8. zapisuje AuditLog.

Attempt_number:

max(existing attempts) + 1

Jeżeli brak prób:

1

Nie używaj globalnego licznika.

---

# 11. CLAIM SUBMISSION

Endpoint:

POST /api/v1/submissions/{submission_id}/claim

Operacja musi być atomowa.

Backend:

1. sprawdza rolę INSTRUCTOR,
2. sprawdza uprawnienia do Task/Stage/PathVersion,
3. sprawdza czy instructor_id jest NULL,
4. przypisuje instruktora,
5. ustawia claimed_at,
6. zmienia status na UNDER_REVIEW,
7. zapisuje AuditLog.

Jeżeli dwóch instruktorów wykona claim równocześnie, tylko jeden może zostać przypisany.

Użyj odpowiedniego mechanizmu transakcyjnego/row locking.

---

# 12. OCENA

Endpoint:

POST /api/v1/submissions/{submission_id}/assessment

Request:

result
comment

Jeżeli:

result = PASSED

comment może być opcjonalny.

Jeżeli:

result = NEEDS_IMPROVEMENT

comment jest wymagany.

Backend:

1. sprawdza czy instruktor jest przypisany,
2. sprawdza uprawnienia,
3. sprawdza aktualny status,
4. tworzy Assessment,
5. zmienia Submission.status,
6. zapisuje AuditLog.

Jeżeli PASSED:

* Submission = PASSED
* Task staje się PASSED dla tego uczestnika
* kolejny Task zostaje AVAILABLE.

Jeżeli NEEDS_IMPROVEMENT:

* Submission = NEEDS_IMPROVEMENT
* uczestnik może utworzyć kolejną próbę.

---

# 13. OSTATECZNE ZALICZENIE

Po:

Submission → PASSED

nie wolno:

* tworzyć kolejnego submission,
* zmieniać wyniku,
* ponownie otwierać zadania.

Jeżeli administrator musi dokonać korekty administracyjnej, musi istnieć osobna funkcja administracyjna i AuditLog.

Nie implementuj jej w MVP, chyba że będzie potrzebna do testów.

# 29. CRITERIA ACCEPTANCE MVP

MVP uznajemy za ukończone dopiero wtedy, gdy:

### Authentication

* [ ] rejestracja działa,
* [ ] logowanie działa,
* [ ] JWT działa,
* [ ] role działają.

### Learning paths

* [ ] można utworzyć ścieżkę,
* [ ] można utworzyć wersję,
* [ ] można utworzyć etap,
* [ ] można utworzyć zadanie,
* [ ] można ustawić kolejność.

### Enrollment

* [ ] admin może przypisać uczestnika do ścieżki,
* [ ] uczestnik widzi swoją ścieżkę.

### Task locking

* [ ] cała ścieżka jest widoczna,
* [ ] pierwsze zadanie jest dostępne,
* [ ] kolejne są zablokowane,
* [ ] zaliczenie odblokowuje następne.

### Submissions

* [ ] uczestnik może wysłać zgłoszenie,
* [ ] można dodać maksymalnie 10 zdjęć,
* [ ] można tworzyć nieograniczoną liczbę prób,
* [ ] każda próba pozostaje w historii.

### Instructor

* [ ] instruktor widzi właściwe zgłoszenia,
* [ ] może przejąć zgłoszenie,
* [ ] tylko pierwszy instruktor może je przejąć,
* [ ] może zaliczyć,
* [ ] może skierować do poprawy.

### Final pass

* [ ] PASSED jest ostateczne,
* [ ] nie można utworzyć kolejnej próby po PASSED,
* [ ] następne zadanie zostaje odblokowane.

### Security

* [ ] frontend nie może ominąć blokad,
* [ ] backend sprawdza uprawnienia,
* [ ] instruktor nie może oceniać nieuprawnionej ścieżki,
* [ ] użytkownik nie może modyfikować cudzych danych.

### Audit

* [ ] kluczowe operacje są zapisywane.

### Tests

* [ ] wszystkie testy automatyczne przechodzą.
